# v0.4 — Fine-tuning & RLHF

*Sessions 13–15, May 2026*

This release adds a complete fine-tuning workflow to EchoHub — collect training pairs from real conversations, fine-tune a local model with Unsloth/QLoRA, evaluate before and after, and export a GGUF model ready to use.

---

## What's new

### Fine-tune section (new nav item)

A dedicated section in the sidebar with three tabs:

**Models** — Browse and download FT-ready models (safetensors/BF16). Toggle between installed local models and Hugging Face search. Each card shows the estimated QLoRA VRAM (not the raw BF16 weight), a live `fits/exceeds GPU` badge, and a download progress bar sourced from the same SSE stream as the rest of the app.

**Profiles** — Organize training pairs into domain-specific profiles. Five builtin profiles: `Dev`, `Reasoning`, `General`, `Analysis`, `Debug`. Each profile has a target pair count, a color, and a progress bar. Three-column layout: profile list → pairs list → pair detail (prompt / chosen / rejected). Pairs can be added manually or saved directly from chat conversations.

**Train** — Configure and launch fine-tune jobs, monitor live logs, and compare before/after eval scores.

---

### Training pairs (RLHF light)

Every assistant message in the chat now has a bookmark button in the footer. Clicking it opens `PairEditor` — an inline editor that pre-fills the prompt (the preceding user message) and the chosen response (the current assistant message), with a textarea for the rejected response. Pairs are saved to SQLite with `profile_id`, `source_conv_id`, and `source_msg_id` for traceability.

Pairs can also be added manually from the Profiles tab.

### Fine-tune jobs

**Configure & Start modal** — hardware-aware defaults:

| VRAM | seq_length | batch | rank |
|------|-----------|-------|------|
| ≥ 24 GB | 2048 | 2 | 32 |
| ≥ 16 GB | 1024 | 1 | 16 |
| ≥ 12 GB (RTX 3060) | 512 | 1 | 16 |
| ≥ 8 GB | 256 | 1 | 8 |

The modal detects the GPU at runtime, shows a live VRAM bar that updates as you change parameters (rank, seq_length), and displays a "Optimal for RTX 3060" banner with the rationale. Every parameter is editable: sequence length, LoRA rank, alpha, target modules, batch size, gradient accumulation, epochs, learning rate, optimizer. A "Reset to recommended" button appears when anything is modified.

**CPU RAM offload** — slider to offload N GB of model layers to system RAM. Triggers 8-bit mode (bitsandbytes). The VRAM bar updates live to reflect the offload.

**Eval before/after toggles** — activate in the modal, auto-find the GGUF version of the base model on HF, and run the full eval pipeline as part of the job.

### Training pipeline

Unsloth runs in an isolated venv (`~/.local/share/echohub/unsloth-env/`), separate from the backend venv. Installation is one-click from the Train tab with live SSE logs. CUDA version is auto-detected (`nvcc --version`) and the correct PyTorch wheel index is selected (cu130 / cu124 / cu121).

Key script parameters:
- `device_map={"": 0}` — all layers on GPU, no CPU dispatch (incompatible with 4bit)
- `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`
- `UNSLOTH_COMPILE_LOCATION=~/.cache/unsloth` — keeps Unsloth's JIT cache out of `src-tauri/` (was causing Tauri hot-reload loops)
- Gradient checkpointing enabled
- `dataloader_pin_memory=False`

All training logs are written to `~/.local/share/echohub/finetune/{job_id}/train.log` in real time and reloaded from disk on app restart.

**Status reliability** — the job status is determined at process exit only:
- returncode 0 → `done`
- returncode non-zero but `adapter_config.json` exists → `done` (Unsloth crashes internally then recovers)
- neither → `error`

On SSE reconnect, if `adapter_config.json` exists on disk, the job is auto-recovered to `done` before any other logic runs.

### Eval before/after pipeline

The eval pipeline runs entirely inside the Fine-tune section — no Chat interaction required.

**GGUF search** — given a BF16 model ID (e.g. `Jackrong/Qwen3.5-9B-Claude-4.6-Opus-Reasoning-Distilled-v2`), the app searches HF for the GGUF version using two queries: `{name}-GGUF` and `{name} GGUF`. Results are sorted: same author first, then by download count. For the top candidate, GGUF files are listed and sorted by preference: Q4_K_M → Q4_K_S → Q5_K_M → Q4_0 → Q8_0.

**Before eval** (runs before fine-tune):
1. Download GGUF Q4_K_M from HF to a temp location
2. Load in llama.cpp (n_gpu_layers=-1)
3. Run all prompts from the selected profile (up to 20)
4. Score responses with `quality_scorer.score_general`
5. Unload model, delete temp GGUF
6. Persist eval record in `finetune_evals` table

**After eval** (runs after LoRA export):
1. Merge LoRA into base weights → safetensors
2. Quantize to GGUF Q4_K_M (llama.cpp `convert_hf_to_gguf.py`)
3. Load the new GGUF
4. Run the same prompts from the same profile
5. Score, unload, persist
6. Display before/after scores side by side

### Download history

Download state is now persisted in SQLite (`download_history` table). History survives backend restarts. The Downloads page shows:
- Active jobs at the top (existing behavior)
- History section below: model name, state badge, size, completion date
- Live VRAM bar on each entry
- Badge "files deleted" (red) if the log entry exists but the model was deleted from disk
- Delete log button (removes the record, not the model files)
- Load button if `state=complete` and files still on disk

### Unsloth venv isolation

Unsloth lives in `~/.local/share/echohub/unsloth-env/` — completely separate from `backend/.venv` and `.venv-vllm`. The install script:
1. Wipes any existing broken venv
2. Detects CUDA version via `nvcc --version`
3. Installs PyTorch with the correct CUDA wheel *first*
4. Then installs Unsloth + deps (no `--no-deps`)

## Known limitations in v0.4

- **GGUF export** depends on `convert_hf_to_gguf.py` from llama.cpp. If not present, the export step fails with a clear error. A future version will bundle or auto-install this script.
- **After eval** requires the export step to succeed (LoRA merge + quantize). If llama.cpp is not installed, after eval is skipped silently.
- **CPU offload** uses 8-bit instead of 4-bit — slower training, but allows larger models on constrained VRAM.
- **1 pair dataset** — training on fewer than 8 effective samples (batch × accum) is technically valid but the model won't generalize. Meaningful results need 50+ pairs per profile.
- **AMD ROCm / Apple Silicon** — untested on real hardware for fine-tuning. The install script detects CUDA only.
