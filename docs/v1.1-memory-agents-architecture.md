# EchoHub v1.1 — Memory + Agents — Architecture complète

Ce document décrit l'architecture unifiée de la mémoire sémantique, des sous-agents, et du harness de validation. Il couvre comment ces trois systèmes s'articulent, comment ils s'activent selon le contexte (chat simple, projets, tool chat), et comment la persistance cross-session fonctionne.

**Prérequis de lecture :** `roadmap.md` (vue globale), `agent-harness-architecture.md` (detail harness).

## 1. Stockage des conversations — ConversationManager

### Remplacement de SQLite

SQLite actuel (`db.py`) stocke messages + metadata dans une DB monolithique. Problèmes : pas de sliding window natif, pas de summarization intégrée, couplage fort entre messages et metadata.

**Nouveau stockage :**

```
~/.echohub/
  conversations/
    {conv_id}.json          ← messages ordonnés, ~10-50KB par conv
    _index.json             ← metadata légère (id, title, date, model, project_id)
  chromadb/
    echohub_memory/         ← layer sémantique (optionnel par conv)
```

### Interface `ConversationManager` (~150 lignes)

```python
# backend/services/conversation_manager.py

class ConversationManager:
    def load(self, conv_id: str) -> Conversation: ...
    def save(self, conv: Conversation) -> None: ...
    def add_message(self, conv_id: str, role: str, content: Any, stats: dict | None = None) -> Message: ...
    def delete_message(self, conv_id: str, msg_id: str) -> None: ...
    def to_context(self, conv_id: str, max_tokens: int = 4096) -> list[dict]: ...
    def summarize_oldest(self, conv_id: str) -> None: ...  # appelle le modèle chargé
    def list_conversations(self, archived: bool = False) -> list[ConvMeta]: ...
    def create(self, id: str, title: str, model_id: str | None, project_id: str | None) -> Conversation: ...
    def delete(self, conv_id: str) -> None: ...
    def update_meta(self, conv_id: str, **kwargs) -> None: ...
```

**`to_context(max_tokens)`** : sliding window pure. Parcourt les messages depuis la fin, accumule les tokens (estimation : `len(content) // 4`), s'arrête quand le budget est dépassé. Retourne toujours `[{role, content}]` format OpenAI.

**`summarize_oldest(conv_id)`** : quand `len(messages) > 40` ou `token_count > 12000`, appelle `POST /v1/chat/completions` avec les N premiers messages et un prompt de résumé. Remplace ces N messages par un seul message `role=system, content="[Summary] ..."`. Déclenché automatiquement dans `add_message` si seuil dépassé.

## 2. Embedding service

### Modèle et instance

- **Modèle :** `nomic-embed-text-v1.5` GGUF — 137MB, multilingual
- **Instance :** llama-cpp-python séparée, `n_gpu_layers=0` (CPU uniquement, zéro impact VRAM)
- **Latence :** ~10ms par embedding à froid, ~3ms ensuite
- **Démarrage :** lazy à la première demande (pas au boot)

```python
# backend/services/embedding_service.py

from llama_cpp import Llama

class EmbeddingService:
    _instance: Llama | None = None

    def _get_model(self) -> Llama:
        if self._instance is None:
            self._instance = Llama(
                model_path=str(EMBED_MODEL_PATH),
                embedding=True,
                n_gpu_layers=0,
                n_ctx=512,
                verbose=False,
            )
        return self._instance

    def encode(self, text: str) -> list[float]:
        return self._get_model().create_embedding(text)["data"][0]["embedding"]

    def encode_batch(self, texts: list[str]) -> list[list[float]]:
        return [self.encode(t) for t in texts]
```

`EMBED_MODEL_PATH` : `~/.echohub/models/nomic-embed-text-v1.5.Q4_K_M.gguf`

Installé automatiquement si absent (même flow que les modèles GGUF existants — `download_manager.py`).

## 3. ChromaDB memory layer

### Collections

```
echohub_memory/
  user_traits          ← préférences, style, habitudes détectées
  conversation_facts   ← faits importants par conv (décisions, contexte clé)
  global_context       ← knowledge cross-conversations
```

Chaque document stocké dans ChromaDB a ces metadata :

```python
{
  "conv_id": "conv_abc123 | global",
  "project_id": "project_xyz | global",
  "type": "user_trait | decision | fact | context | error_learned",
  "importance": 7,          # 1-10
  "created_at": "2026-...",
  "source_msg_id": "msg_042"
}
```

### Service

```python
# backend/services/memory_service.py

class MemoryService:
    def store(self, content: str, type: str, conv_id: str = "global",
              project_id: str = "global", importance: int = 5) -> str: ...
    
    def search(self, query: str, conv_id: str | None = None,
               project_id: str | None = None, limit: int = 5) -> list[MemoryResult]: ...
    
    def consolidate(self, conv_id: str) -> ConsolidationResult: ...
    
    def delete(self, memory_id: str) -> None: ...
    
    def stats(self) -> MemoryStats: ...
```

**`search`** : si `conv_id` et `project_id` sont None → recherche globale cross-sessions. Si fournis → filtre par metadata. `limit=5` par défaut (ne pas saturer le contexte).

**`consolidate`** : crée un nouveau contexte isolé, appelle le modèle avec les N dernières mémoires d'une conv, demande de dédupliquer et synthétiser. Remplace les anciennes entrées par les nouvelles. Notification UI "Consolidation en cours — sujet : X".

### Activation par conversation

`memory_enabled: bool` dans `{conv_id}.json`. Modifiable depuis :
- Toggle dans le header du chat
- Settings > Memory > Vue par conversation

## 4. Injection mémoire dans le prompt

### Flow complet avant chaque inférence

```python
# backend/services/prompt_builder.py

async def build_prompt(conv_id: str, user_message: str) -> list[dict]:
    conv = conversation_manager.load(conv_id)
    
    messages = []
    
    # System : identité + instructions mémoire
    if conv.memory_enabled:
        messages.append({"role": "system", "content": SYSTEM_WITH_MEMORY})
        
        # Récupérer top 5 mémoires pertinentes
        memories = memory_service.search(
            query=user_message,
            conv_id=conv_id,
            project_id=conv.project_id,
            limit=5
        )
        if memories:
            mem_block = "\n".join(f"[{m.type}] {m.content}" for m in memories)
            messages.append({
                "role": "system",
                "content": f"Relevant memories from your knowledge base:\n{mem_block}"
            })
    else:
        messages.append({"role": "system", "content": SYSTEM_STANDARD})
    
    # Sliding window des messages de la conv
    history = conversation_manager.to_context(conv_id, max_tokens=3000)
    messages.extend(history)
    
    # Message courant
    messages.append({"role": "user", "content": user_message})
    
    return messages
```

### System prompts

**Avec mémoire :**
```
You have access to a semantic memory system — your persistent knowledge base across
all conversations. Use search_memory(query) to retrieve relevant context before
answering on topics you've discussed before. Use store_memory(content, type) to
save important new facts, decisions, or preferences the user shares.

Memory types: user_trait, decision, fact, context, error_learned.
Search is cross-session by default unless the user specifies "in this conversation".

You also have access to invoke_agent(task, harness) to delegate isolated subtasks
to a sub-agent running on the same model with a clean context.
```

**Sans mémoire :**
```
You are EchoHub's assistant. You have access to tools via skills and MCP servers.
Use invoke_agent(task, harness) to delegate isolated subtasks when needed.
```

### Dispatch dans `tool_service.py`

```python
# Ajouter dans tool_service.py

async def dispatch_tool(name: str, args: dict, conv_id: str) -> str:
    match name:
        case "search_memory":
            results = memory_service.search(args["query"], scope=args.get("scope", "global"))
            return json.dumps([r.to_dict() for r in results])
        
        case "store_memory":
            mem_id = memory_service.store(
                content=args["content"],
                type=args["type"],
                importance=args.get("importance", 5),
                conv_id=conv_id
            )
            return json.dumps({"stored": True, "id": mem_id})
        
        case "consolidate_memory":
            result = await memory_service.consolidate(conv_id)
            return json.dumps(result.to_dict())
        
        case "invoke_agent":
            result = await agent_service.invoke(
                task=args["task"],
                harness=args.get("harness", "read_strict"),
                tools=args.get("tools"),
                conv_id=conv_id
            )
            return json.dumps(result.to_dict())
        
        case _:
            # Déléguer aux dispatchers existants (MCP, etc.)
            return await existing_dispatch(name, args, conv_id)
```

## 6. Sub-agents et harness

### `invoke_agent` — implémentation

```python
# backend/services/agent_service.py

async def invoke(task: str, harness: str, tools: list[str] | None, conv_id: str) -> AgentResult:
    # Sélectionner les tools selon le harness
    tool_set = HARNESS_TOOLS[harness]
    if tools:
        tool_set = [t for t in tool_set if t in tools]
    
    # Construire le contexte isolé — ZÉRO messages du conv parent
    messages = [
        {"role": "system", "content": SUB_AGENT_SYSTEM[harness]},
        {"role": "user", "content": task}
    ]
    
    # Inférence sur le même modèle déjà chargé
    response = await call_loaded_model(messages, tools=tool_set, max_tokens=2048)
    
    # Parser le résultat structuré
    result = parse_agent_result(response)
    
    # Si file edits → harness intercepte automatiquement
    if result.has_file_mutations:
        validation = await universal_harness.validate(result.mutations)
        if validation.overall == "fatal":
            # Retry loop (max 5)
            ...
        result.validation = validation
    
    return result
```

### Harness profiles

| Profile | Tools disponibles | Usage |
|---------|-------------------|-------|
| `read_strict` | `find`, `read_file`, `grep`, `list_dir` | Lecture seule — analyse, extraction |
| `write_validated` | tout `read_strict` + `edit_file`, `create_file`, `delete_file` | Écriture avec validation complète |
| `shell_safe` | tout `write_validated` + `run_command` (allowlist) | Shell restreint pour build/test |

### Universal harness — résumé

Voir `agent-harness-architecture.md` pour le détail complet. Résumé :

```
file edit → LANGUAGE DETECTOR → SYNTAX → LINT → TYPES → TESTS
                                     ↓
                            result normalisé JSON
                            { overall: "ok|warning|error|fatal", actionable: [...] }
                                     ↓
                       injecté dans contexte sub-agent AVANT de continuer
```

Max 5 retries par mutation. Si `overall == "fatal"` après 5 retries → escalade à l'orchestrateur.

## 7. Modes d'activation selon le contexte

### Chat normal (sans skills MCP)

- `memory_enabled` sur la conv → inject memories + expose `search_memory`, `store_memory`
- `invoke_agent` disponible si un modèle est chargé (llama.cpp ou vLLM)
- Harness : `read_strict` uniquement (pas de file edits depuis le chat normal)

### Tool chat (skills MCP actifs)

- Même logique mémoire
- `invoke_agent` avec tous les harness disponibles
- Les tools MCP existants restent disponibles
- Sub-agents peuvent appeler des tools MCP s'ils sont dans leur tool set

### Projets

- `project_id` set sur la conv → mémoire scoped au projet en plus du global
- `search_memory` avec `scope="project"` retourne uniquement les mémoires de ce projet
- Harness `write_validated` activé par défaut (projets = workspace de travail)
- Contexte projet injecté automatiquement : arborescence, README si présents

## 9. Ordre d'implémentation strict

```
Step 1 — ConversationManager
  - conversation_manager.py (~150 lignes)
  - Migration SQLite → JSON au boot
  - Mettre à jour conversations.py router
  - Mettre à jour useConversations.ts / useProjectConversations.ts
  → Tester : CRUD conversations, messages, sliding window

Step 2 — Embedding service
  - embedding_service.py
  - Download auto nomic-embed-text GGUF si absent
  → Tester : encode("hello world") retourne un vecteur de 768 floats

Step 3 — ChromaDB + memory_service
  - memory_service.py
  - Collections : user_traits, conversation_facts, global_context
  - Routes : POST /memory/store, GET /memory/search, POST /memory/consolidate
  → Tester : store → search retrouve le doc

Step 4 — Tool dispatch
  - Ajouter search_memory, store_memory, consolidate_memory, invoke_agent dans tool_service.py
  - agent_service.py (invoke sans harness d'abord)
  → Tester : appel invoke_agent depuis useToolChat

Step 5 — Universal harness
  - harness_service.py : language detector + validation pipeline
  - Brancher sur invoke_agent pour tout file edit
  → Tester : edit d'un .py avec erreur de syntaxe → agent la reçoit et corrige

Step 6 — Settings > Memory UI
  - MemoryTab.tsx dans Settings
  - Toggle dans ChatHeader
  → Tester : toggle par conv, affichage stats

Step 7 — System prompts conditionnels
  - prompt_builder.py
  - Brancher dans inference.py (remplacement de la construction prompt actuelle)
  → Tester : avec mémoire → instructions injectées, without → prompt classique
```

**Règle :** chaque step est testable et stable avant de passer au suivant.
