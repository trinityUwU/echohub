# v0.9 — Load Profiles, Multi-GPU & Speculative Decoding

## What this is

v0.9 focuses entirely on GPU utilization. The load modal gets four one-click profiles that
configure every parameter automatically, two new VRAM controls (`offload_kqv`, `n_batch`),
native multi-GPU support for both engines, and three modes of speculative decoding.

---

## Load profiles

Four profiles selectable before loading a model. Each fills all sliders automatically.

| Profile | VRAM target | GPU layers | KV quant | offload_kqv | n_batch | Context |
|---------|-------------|-----------|---------|------------|---------|---------|
| ⚡ Performance | ~92% total | Full (-1) | Q8_0 | off | 512 | Fixed |
| ⚖ Balanced | ~50% total | Partiel auto | Q8_0 | off | 256 | Fixed |
| 🎮 Gaming | ~3 GB | Partiel auto | Q4_0 | on | 128 | Smart cap |
| 🪶 Minimal | ~1.5 GB | Partiel auto | Q4_0 | on | 64 | Smart cap |

GPU layers are computed dynamically: `estimateLayers(paramsBillion) × gpuLayersPct / 100`.
On Qwen3-9B Q4_K_M (~5 GB) with Gaming mode → ~3–4 layers on GPU, ~8.5 GB free for other
workloads.

Profile cards display "X% GPU · ~Y GB free" calculated in real time from the selected model.
All profiles activate n-gram speculative decoding by default via `applyProfile`.

## VRAM parameters

### offload_kqv

Moves the KV cache to system RAM instead of VRAM.

```python
Llama(offload_kqv=True)
```

- **Saving**: 100% of the KV cache footprint (e.g. ~0.8 GB on an 8B model at ctx 4096)
- **Cost**: slight PCIe latency on attention (~5–15%)
- **When to use**: Gaming and Minimal profiles, or any time VRAM is the limiting factor

The VRAM bar shows a separate green "KV cache (RAM)" column when enabled, with preview
updating in real time as you adjust context length.

### n_batch

Batch size for prompt evaluation (prefill).

| Value | Use case |
|-------|----------|
| 512 | Default — fast prefill, standard VRAM |
| 256 | Compromise |
| 128 | MoE models or tight VRAM |
| 64 | Last resort |

Each option shows its tradeoffs inline in the modal.

### Smart cap (context mode)

Replaces the old "Adaptive" mode which passed `null` as n_ctx and caused llama.cpp to crash
with "tokens exceed context window of 4096".

Smart cap computes the maximum context that fits in available VRAM after weights:

```
available_vram = total_vram - weight_footprint - cuda_overhead
n_ctx = floor(available_vram / kv_cache_per_token)
```

With `offload_kqv` on, KV cache no longer consumes VRAM — Smart cap can reach 32K on a
12 GB card with a mid-size model.

The alternative is **Fixed** mode: allocates the exact n_ctx set in the slider at load time.

## Speculative decoding

Available in the load modal for llama.cpp engine only. Three modes:

### N-gram lookup (default on all profiles)

```python
Llama(draft_model=LlamaPromptLookupDecoding(num_pred_tokens=10))
```

- Gain: ~1.3x on repetitive outputs, code, RAG
- VRAM cost: zero
- No extra model required
- Enabled by default in all four load profiles

### MTP self-speculative

```python
Llama(draft_model=LlamaDraftModel(llm=_draft, n_pred=N))
```

- Gain: ~1.5x on coding and structured outputs
- Requires MTP heads in the GGUF (Qwen3, DeepSeek-V3)
- Auto-detected: `GET /inference/llama/mtp-support?model_id=...` scans the first 64 KB
  of GGUF metadata for `b'mtp'` / `b'num_nextn_predict'`
- Option is grayed out with a tooltip if the GGUF is incompatible

### Draft model (external)

```python
_draft = Llama(model_path=draft_path, n_ctx=n_ctx, n_gpu_layers=n_gpu, n_batch=32)
Llama(draft_model=LlamaDraftModel(llm=_draft, n_pred=N))
```

- Gain: ~2x on coding
- Input: GGUF path for the draft model
- Slider: n_pred_tokens (2–16), visible for MTP and draft model modes

## Multi-GPU

### llama.cpp — tensor_split

New `backend/services/multi_gpu.py`:

- `detect_all_gpus()` — queries nvidia-smi (NVIDIA) and rocm-smi (AMD), silent fallback
- `compute_tensor_split()` — split proportional to each GPU's VRAM, equal split if VRAM unknown
- `get_multi_gpu_config()` — returns `{gpu_count, gpus, tensor_split, total_vram_mb}`

Endpoint: `GET /inference/multi-gpu-config`

At load time:
```python
Llama(tensor_split=[0.5, 0.5], main_gpu=0)
```

The VRAM bar uses the combined total across all GPUs.

**Frontend**: on modal mount, `getMultiGpuConfig()` is called. If `gpu_count > 1` and
engine is llama, a green banner shows "N GPUs detected — tensor split enabled" with the
percentage per GPU.

**Example**: 2×RTX 4090 (2×24 GB = 48 GB total) — tensor_split computed automatically,
70B models load natively.

### vLLM — tensor_parallel_size

```bash
vllm serve ... --tensor-parallel-size N --pipeline-parallel-size N
```

Injected into the vLLM subprocess command in `vllm_service.py`.

In the modal (engine vLLM, gpu_count > 1): a selector from 1 to N GPUs. Each GPU removed
decreases TP size by 1. `pipeline_parallel_size` is wired but has no UI yet (relevant for
3+ GPUs with models >70B).

## Bug fixes

**`resolvedNGpuLayers` returning null for partial GPU allocation**
Any value between 0–100% returned `null`, which the backend interpreted as `-1` (full GPU).
Fix: conversion now goes through `estimateLayers()` which returns a concrete integer.

**"Adaptive" context mode crashing llama.cpp**
Mode passed `null` as n_ctx. llama.cpp raised "tokens exceed context window of 4096".
Replaced entirely by "Smart cap" which computes a real context value before load.
