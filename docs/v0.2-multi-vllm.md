# v0.2 — Multi-engine vLLM

**Status: Stable**  
**Released: 2026-05-17**

---

## The problem this solves

vLLM releases new versions every few weeks. Each version adds support for new model architectures, fixes quantization bugs, and improves performance. But you can't just upgrade — a newer vLLM might break models that worked fine on the previous version.

In v0.1, EchoHub shipped with one vLLM version (0.21.0). If a model needed a different version, you were stuck.

v0.2 fixes this completely.

---

## What shipped in v0.2

### Multiple vLLM versions, side by side

Each vLLM version lives in its own isolated Python environment:

```
~/.local/share/echohub/vllm-envs/
  0.21.0/    ← ships with the app
  0.8.5/     ← installed later for older model support
  0.22.0/    ← installed for newer architectures
```

They don't interfere. You can have three versions installed and each one handles the models it's compatible with.

**Implementation:** `backend/services/vllm_manager.py` — scans venvs, measures disk size, validates that each version is actually operational (not just installed), and handles install/delete with safety guards.

### Automatic compatibility routing

When you load a model, EchoHub checks which vLLM version it needs and uses that one. You don't pick the version — the app does.

The routing chain:
1. `backend/routers/models.py` `/compatibility/:id` → fetches `config.json` from HF, checks architecture against vLLM's supported list, detects multimodal+AWQ conflicts, returns `required_vllm_version`
2. `backend/services/engine_router.py` → resolves the correct Python executable via `vllm_manager.get_python_for_version()`
3. `backend/services/vllm_service.py` → spawns vLLM subprocess with `python_override`

If no compatible version is installed, you see the install button directly in the model panel — before you waste time downloading.

### Settings / Engines tab

Full visibility into what's installed:
- Version number, disk usage, operational status (import-tested, not just file-present)
- Number of model architectures covered
- Coverage warning if installed versions cover < 70% of common architectures
- Delete protected if it's the last operational version

### Onboarding wizard

Six-step wizard on first launch:
1. **Welcome** — what EchoHub is and why it's different
2. **Storage** — exact paths, sizes per component, no surprises
3. **Hardware** — detected GPU, VRAM, what's available on your machine
4. **Engines** — multi-venv explained, currently installed versions
5. **Compatibility** — the three compatibility states (✓ / ⚠ needs version / ✗ no engine)
6. **Done** — direct link to Discover

Replay anytime from Settings → About → "Replay tutorial".

### Configurable paths

All storage paths are now configurable from Settings → Paths:
- **Models directory** — where downloaded models live
- **vLLM environments** — where engine venvs are stored

Changing a path triggers an **assisted migration**: the app copies files to the new location, verifies each one, shows live progress. If the app crashes mid-migration, it resumes automatically on next launch. If a file is unreadable, it's flagged for re-download.

### Universal start.sh

Clone the repo and run `./start.sh`. On any supported platform:

- Detects OS (Arch, Debian/Ubuntu, Fedora, macOS)
- Installs missing system dependencies (webkit2gtk, cmake, gcc…)
- Installs Rust via rustup if absent
- Installs Bun if absent
- Creates Python venv and compiles llama-cpp-python with the right backend (CUDA with architecture detection on Arch, ROCm, Metal, or CPU)
- Migrates the legacy `.venv-vllm/` to `~/.local/share/echohub/vllm-envs/0.21.0/` if needed
- Detects Wayland vs X11 and sets the right display backend
- Launches the app

`./start.sh --dev` for hot-reload dev mode. `./stop.sh` to stop everything.

## Known limitations in v0.2

- **Automatic version install on incompatibility** — intentionally not automatic. Loading 7 GB without explicit confirmation is a bad UX pattern. The app shows a clear install button instead.
- **Migration of legacy vllm-envs in start.sh** does not yet update `config.json` automatically — minor edge case, fixed in a future patch.
- **Apple Silicon GPU usage** — `powermetrics` requires `sudo` on macOS. If unavailable, GPU utilization shows as 0% (VRAM total is still accurate via `sysctl`).
- **AMD ROCm** — functional but not tested on a real AMD setup. rocm-smi JSON format may vary by driver version.
