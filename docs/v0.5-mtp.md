# v0.5 — MTP support

Status: Stable
Released: 2026-05-19

---

## What MTP is

Multi-Token Prediction means a model has extra prediction heads baked into its weights. Instead of predicting one token at a time, the model produces several candidate continuations in parallel. llama.cpp uses these as speculative decoding hints: it generates a draft and verifies it in a single forward pass, cutting the number of full forward passes needed.

On a 12GB RTX 3060, a Qwen3.5 9B Q4_K_M goes from ~35 tok/s to 50–60 tok/s. No quality change, no extra VRAM, no settings to touch. If the model has MTP tensors and you're running llama.cpp, it just works.

MTP is baked in at training time. If the base weights don't include MTP heads, there's nothing to enable — you can't add it after the fact.

---

## Which models have it

Qwen3 and Gemma3 both ship with MTP heads. If you're running a Qwen3 model through llama.cpp, MTP is already active.

Older models like Llama 2, Mistral 7B v0.1, and most pre-2025 releases were not trained with MTP. The way to tell is by looking at the tensor list inside the GGUF — MTP tensors are named `blk.N.nextn.*`. No matches, no speculative decoding.

---

## How detection works

For local GGUFs (Library, fine-tune export), EchoHub parses the GGUF binary and scans the tensor index at the top of the file. It stops as soon as it finds a tensor name containing `nextn`. The scan takes a few milliseconds and doesn't touch the weights.

For models in Discover before download, EchoHub falls back to a name heuristic: model IDs containing `qwen3` or `gemma3` are flagged as likely MTP-capable. It's an approximation, but an accurate one for the current model landscape.

---

## The badge

An MTP badge shows up in Discover (on Qwen3/Gemma3 model cards), Library (on GGUFs confirmed to have MTP tensors after binary scan), and ModelPickerModal (alongside engine and quantization info). It's display-only — the engine handles everything else automatically.

---

## Fine-tune export

If you fine-tune a Qwen3 or Gemma3 model and export to GGUF, the MTP tensors come through. The pipeline (LoRA merge → BF16 safetensors → GGUF BF16 → Q4_K_M) passes the full merged model, which keeps the MTP heads from the base weights. `convert_hf_to_gguf.py` handles MTP-capable architectures natively.

After export, EchoHub scans the output GGUF and reports `MTP_DETECTED:true/false` in the export log. The `done` event carries `has_mtp: true/false` so the badge appears on the exported model immediately.

---

## Known limitations

MTP only works with the llama.cpp engine. If you load a Qwen3 AWQ model through vLLM, MTP isn't available — vLLM doesn't implement MTP-based speculative decoding.

GGUFs downloaded before v0.5 weren't scanned at download time. They get scanned the first time their card is rendered in Library. If you fine-tuned a Qwen3 model before v0.5 and exported GGUF, the MTP tensors are likely present anyway — the old pipeline didn't strip them, they just weren't detected.
